## Рамки

Это поэтапный аудит исходного кода приложения GRUZLI. Регистрация и авторизация в текущей Supabase-реализации исключены из исправлений: они будут реализованы заново в целевой российской инфраструктуре. Текущая Supabase-БД не является целевой; миграция данных не планируется (clean start). Не считать этот документ аудитом production-данных или работающего окружения: доступа к production БД, аккаунтам и runtime-логам в рамках этого прохода нет.

Целевая архитектура: Amvera Cloud, Node.js API, PostgreSQL, собственный realtime/WebSocket, постоянное файловое хранилище. Публичный deployment не переключать до завершения миграции и приемочных проверок.

## Снимок репозитория

- Frontend: React 18, TypeScript, Vite, React Router, TanStack Query, Framer Motion.
- Текущий data layer: `@supabase/supabase-js`; фронтенд напрямую вызывает таблицы, RPC, Edge Functions, Realtime и Storage.
- В дереве `main`: 166 файлов под `src/`, 93 SQL-миграции Supabase, 26 каталогов Edge Functions с `index.ts` (точный счёт по дереву на дату аудита).
- npm scripts: lint, typecheck, Vitest, Vite build. CI workflow также запускает Playwright Chromium.
- В текущей ветке обнаружены два Vitest-файла; один из них — тест-заглушка `expect(true).toBe(true)`. Playwright содержит два smoke-теста оболочки/demo-ленты, но не покрывает ключевые бизнес-транзакции.

## Подтверждённый дефект P1: отклик на заказ без назначенного диспетчера

Файл: `src/hooks/useRespondToJob.ts`.

До исправления приложение вызывало RPC `worker_submit_response` (создание отклика), и только после этого проверяло `job.dispatcher_id`. Если заказ не назначен диспетчеру, UI показывал отказ, но запись отклика уже могла быть создана. Это нарушает dispatcher-first workflow и создаёт риск «осиротевших» откликов.

Дополнительный дефект в том же потоке: ошибка RPC `get_weekly_completed_jobs` игнорировалась. При сбое проверки лимита приложение продолжало отклик, то есть ограничение могло обходиться из-за ошибки backend.

Исправление в этой ветке:
- проверка назначения диспетчера перенесена до любых записей;
- проверка недельного лимита работает fail-closed: при ошибке или пустом результате действие останавливается и пользователь получает сообщение.

## Другие подтверждённые зоны риска — требуют полного прохода

1. **Лента заказов:** начальный запрос фильтрует `status = active`, но realtime INSERT в базовой версии добавляет любую новую запись без проверки статуса. Это может показать черновые/неактивные заявки. Открытый PR #11 содержит исправление INSERT/UPDATE/DELETE, но его нужно перепроверить и включить в общий план переноса realtime.
2. **Создание заказа:** в базовой версии проверки формы ограничены названием и положительной ставкой; серверный RPC остаётся последней защитой. Открытый PR #9 добавляет валидацию диапазонов, времени, количества исполнителей и защищает от повторного submit. Требуется проверить соответствие бизнес-правилам и перенести в новый API, а не сливать Supabase-специфичный код без адаптации.
3. **Загрузка заказов:** открытый PR #8 улучшает обработку ошибок чтения заказов/откликов. Нужно проверить все ветки ошибок и не допускать отображения пустого списка как будто данных действительно нет.
4. **Подбор исполнителей:** PR #15 вводит scoring по навыкам, рейтингу, опыту, верификации и активности. Текущие unit-тесты слишком узкие: тест Premium не сравнивает разные значения Premium; токенизация через частичное включение может давать ложные совпадения; алгоритм требует проверки на русских словоформах и реальных профилях. Не сливать без усиления тестов и проверки справедливости ранжирования.
5. **Профили и статистика:** PR #7 описывает существенные дефекты рейтингов, метрик и действий профиля, но содержит старую auth/Storage/RLS миграцию и не может быть принят целиком в новую архитектуру. Бизнес-правила статистики и рейтингов нужно перенести в API/domain layer и покрыть тестами.
6. **Чаты, уведомления, документы, звонки, платежи/балансы, админ-функции:** требуют отдельной трассировки каждого действия до источника данных, серверной операции и проверки полномочий.

## Открытые изменения

- PR #8, #9, #10, #11 — полезные исправления бизнес-потоков в старом Supabase-слое. Их нужно оценить по отдельности и перенести нужную логику в новый API; не выполнять массовое слияние.
- PR #14 — черновая миграция Amvera. Документация прямо указывает, что фронтенд ещё содержит Supabase-вызовы. CI success на ветке не означает функциональную готовность миграции.
- PR #15 — scoring исполнителей; требуется дополнительная валидация алгоритма и тестов.
- PR #7 и auth-related PRs — вне текущего объёма в части старой регистрации/авторизации; бизнес-дефекты из них остаются в аудите.

## Правило готовности

Ни одна функция не считается исправленной только потому, что UI показывает success или сборка проходит. Для каждой критической операции нужны серверная проверка инвариантов, тесты успешного/ошибочного/повторного/параллельного выполнения и подтверждение CI. Production readiness не заявляется без end-to-end проверки на целевом Amvera окружении.
