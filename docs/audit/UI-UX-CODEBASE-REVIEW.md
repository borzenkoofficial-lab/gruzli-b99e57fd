# GRUZLI — UI/UX и frontend maintainability review

Дата: 2026-11-21  
Основание: статический анализ исходников `main`; не является визуальным QA production-версии.

## Вывод

В GRUZLI уже есть самостоятельная визуальная система и отдельные mobile/desktop оболочки. Проблема не в необходимости полного редизайна, а в накопившихся CSS-переопределениях и крупных компонентах, из-за которых точечные изменения могут непредсказуемо влиять на другие экраны.

Не менять визуальную концепцию без причины. Следующий этап — стабилизация дизайн-токенов, каскада, responsive behavior и экранных состояний с сохранением текущего арт-дирекшена.

## Измеримые факты

### CSS
Файл `src/gruzli-editorial.css`:
- 180 559 символов, 6 508 строк;
- 1 295 обычных CSS rule blocks (без keyframe steps), 925 уникальных selector headers;
- 1 212 использований `!important`;
- 91 media query;
- 204 selector headers повторяются в нескольких местах.

Build cleanup от 2026-11-21:
- Удалены два orphan selector headers, из-за которых CSS parser считал последующий `@media` неожиданным токеном.
- Экранированы квадратные скобки и десятичная точка в utility selectors.
- Все `@media(` приведены к корректному синтаксису `@media (`.
- Последний main build: **0 CSS syntax warnings** и **0 duplicate dynamic-import chunk warnings** после выноса notification storage helpers из screen и удаления повторных preloads.
- Осталось не блокирующее предупреждение: `caniuse-lite` / Browserslist data устарели примерно на 17 месяцев; обновление browser dataset запланировано отдельно.
- Наиболее часто повторяются: `.gruzli-job-card` (11 правил), `.bottom-nav-pill` (10), `.app-scroll` (9), `.app-shell` (9), `.desktop-main-inner` (8), `.bottom-nav-wrapper` (8), `.gruzli-mobile-feed` (8), `:root` (5).

Это подтверждает высокую плотность переопределений. Сами по себе повторные правила не всегда ошибка, но вместе с большим количеством `!important` повышают риск каскадных регрессий и усложняют предсказуемое развитие интерфейса.

### Структура экранов
Крупные экраны смешивают загрузку данных, realtime-подписки, бизнес-логику, локальное состояние и JSX в одном файле:
- `DispatcherCabinetScreen.tsx` — около 1 377 строк;
- `ProfileScreen.tsx` — около 1 079 строк;
- `RealChatScreen.tsx` — около 970 строк;
- `FeedScreen.tsx` — более 800 строк;
- `OrdersScreen.tsx` — более 700 строк.

Это увеличивает цену изменений и усложняет изолированное тестирование. Выносить следует по доменным границам: query/service hooks, state machines, view components, а не дробить файлы механически.

### Адаптивность и QA
- Глобальная оболочка использует фиксированную высоту viewport и `overflow: hidden`, а внутренние области имеют собственную прокрутку. Такая схема допустима для native-like PWA, но требует тестов вложенной прокрутки, клавиатуры, safe areas и длинных экранов.
- Breakpoints в editorial CSS встречаются на 340, 390, 430, 480, 767, 768 и 1200 px.
- Playwright smoke tests сейчас проверяют запуск demo workspace, mobile shell при 390 px и desktop shell при 1024/1440 px с проверкой горизонтального overflow. Они пока не проверяют tablet 768 px, клавиатуру, длинные формы, модальные окна, chat interactions и полноценные сценарии всех трёх ролей.
- Есть правила `prefers-reduced-motion`, их нужно сохранить при дальнейшей работе с анимациями.

## Приоритетные UI/UX задачи

### P1 — стабилизировать каскад без редизайна
1. Зафиксировать единственные источники истины для цветовых, типографических, радиусных, spacing и elevation tokens.
2. Разобрать дублирующиеся правила для feed cards, bottom navigation, app shell и desktop layout.
3. Постепенно удалить `!important`, заменяя его понятной специфичностью и компонентными слоями. Не делать массовую замену одним коммитом.
4. Разделить CSS по доменным компонентам и оболочкам с контролируемым порядком импорта.
5. Добавить визуальные регрессионные проверки для ключевых экранов до/после изменений.

### P1 — проверка состояний и доступности
- Loading, error, empty, success и offline состояния должны различаться.
- Проверить focus-visible, keyboard navigation, aria labels, dialog focus trap и контраст.
- Проверить длинные ФИО, адреса, описания, длинные сообщения и большие числа.
- Проверить кликабельные зоны на телефонах и масштабирование 100–150%.
- Проверить анимации при `prefers-reduced-motion`.

### P2 — декомпозиция экранов
- Выделить data hooks/repositories из экранов.
- Вынести конечные автоматы заказов и откликов в доменный слой.
- Разделить chat transport, message state и presentation.
- Убрать прямые Supabase-запросы из UI в ходе миграции на typed API client.
- Сохранить текущие визуальные компоненты и переходы, если нет подтверждённого UX-дефекта.

## План визуального QA

Минимальная матрица viewport:
- 340×740 — узкий мобильный экран;
- 390×844 — базовый мобильный;
- 430×932 — большой мобильный;
- 768×1024 — tablet breakpoint;
- 1024×768 — компактный desktop;
- 1440×900 — основной desktop;
- 1920×1080 — широкий desktop.

Ключевые сценарии:
1. Лента: загрузка, фильтр, поиск, карточка, открытие заказа, отклик.
2. Заказы: пусто, активный заказ, завершённый заказ, ошибки загрузки.
3. Кабинет диспетчера: список заявок, набор, статистика, завершение заказа.
4. Чаты: длинный диалог, вложение, голосовое сообщение, клавиатура, модалка звонка.
5. Профиль/картотека: длинные данные, аватар, навыки, доступность.
6. Создание заказа: все поля, валидация, preview, клавиатура, safe-area.

Для каждого сценария нужны скриншоты, отсутствие горизонтального overflow, корректные safe areas, читаемость текста и стабильность прокрутки.

## Ограничения проверки

На этом этапе проанализированы CSS/TSX исходники и существующие тесты. Визуальный screenshot audit реального устройства/production-сессии ещё не выполнен. Не утверждать, что перечисленные CSS-риски уже воспроизведены как конкретные визуальные дефекты; это технические причины для целевого QA.
